# A hand-written tokenizer highlights the Approval message, not a library

`src/highlight.ts` renders the Approval message (`src/tools.ts`'s two fixed
shapes — the `http_request` line, and the `run_with_secret` command/env-var
lines) as syntax-highlighted HTML via a small set of regexes matched against
those exact shapes, ported from the design system's `ApprovalScreen.jsx`
prototype. It is not a general-purpose highlighter and doesn't try to be.

Considered a real highlighter library (e.g. a shell/bash grammar via
highlight.js or Prism) for more robust, general tokenizing. Rejected: it would
need to be vendored locally (no CDN — see ADR 0003/0004's offline
requirement), adds real weight for a page that renders in milliseconds, and
solves a harder problem than the one that exists here. The Approval message
has exactly two shapes, both generated by this codebase's own `tools.ts`, not
arbitrary shell script — a general shell grammar would still need custom rules
layered on top to distinguish "this is a secret id" from "this is an argv
token," which is the only part that actually matters for a human reviewing an
Approval. A ~90-line regex tokenizer matched to those two shapes is smaller,
has no dependency to audit, and is exactly as capable as the actual problem
requires — consistent with every other "smallest correct thing, vendored
locally" choice already made in this project.

The trade-off, accepted deliberately: if `tools.ts` ever grows a third message
shape, `highlight.ts`'s fallback renders it as one plain (still escaped, still
safe) line rather than mis-highlighting it — correct but undecorated until the
tokenizer is extended to match. `test/highlight.test.ts` locks this fallback
behavior in, along with the security property that actually matters: every
text fragment is escaped before being wrapped in a span, so highlighting can
never become the injection point (the message is untrusted-ish — built from
tool args a caller controls, like a target host).
